# ADR-0002：以稳定键和乐观并发检查实现关系表安全编辑

## 状态

Accepted

## 背景

在表格里直接改数据是数据库客户端最高频的操作之一，也是最容易做错的一个：把任意查询
结果当成可更新数据，轻则改错行，重则静默丢失并发写入。本 ADR 为 PostgreSQL、
MySQL / MariaDB 和 SQLite 定义这个能力的安全边界。主要风险包括：

- 分页结果没有稳定顺序，翻页时重复或遗漏行。
- 没有主键的表无法唯一定位用户正在编辑的行。
- 从加载到提交之间，其他事务可能已经修改或删除同一行。
- 直接拼接单元格值会产生 SQL 注入、转义错误和二进制数据损坏。
- 一批变更执行到一半失败会留下部分提交。
- `JOIN`、聚合、CTE、视图或计算列通常不能可靠映射回单一源行。

## 决策

### 1. 表浏览使用独立的服务端分页契约

`DatabaseSession` 提供表元数据、分页浏览、变更规划和应用变更四个能力入口。每次页面加载执行：

1. 使用相同筛选条件的精确 `COUNT(*)`。
2. 带稳定排序、`LIMIT` 和 `OFFSET` 的页面查询。

结构化筛选值使用绑定参数。原始 `WHERE` / `ORDER BY` 先按当前方言包装解析，拒绝多语句和越界
子句，再作为用户明确输入的表达式执行。

### 2. 只有稳定、非空的唯一键可以标识可编辑行

驱动读取列、主键和唯一索引元数据。选择规则为：

1. 优先主键。
2. 否则选择组成列全部声明为 `NOT NULL` 的唯一键。
3. 多个候选键按列数和名称确定性选择。

部分索引、前缀索引和表达式索引不作为稳定键。视图和没有稳定键的表可浏览但只读。

### 3. 所有变更先规划，再执行预览中的同一份计划

桌面端将新增、更新和删除暂存在内存中。驱动把变更转换为：

- 参数化 SQL。
- 与占位符顺序一致的类型和值参数。
- 删除、更新、新增的确定性执行顺序和摘要。

界面展示该计划；确认应用时把同一个 `TableChangePlan` 交回驱动，不重新从界面文本生成 SQL。
用户继续编辑会使已有计划失效。

### 4. 使用原始值进行乐观并发检查

更新语句的条件包含稳定键以及所有被修改列的原始值。删除语句包含稳定键以及查询结果中所有
直接来源列的原始值。不同数据库使用各自的 NULL-safe 比较：

- PostgreSQL：`IS [NOT] DISTINCT FROM`。
- MySQL / MariaDB：`<=>`。
- SQLite：`IS [NOT] DISTINCT FROM`。

每条更新或删除必须恰好影响一行。影响零行或多行都视为冲突。

### 5. 一批变更在单个事务中原子提交

驱动在一个事务中执行全部计划语句。任一语句失败、发生冲突、超时或取消时不提交；冲突返回
结构化 `DriverError::Conflict`。提交成功后，表浏览重新加载当前服务端页；查询结果重新执行原查询。

### 6. 查询结果采用保守的可编辑性分析

SQL AST 只接受单一普通表来源。直接列和别名列可映射回源列，计算列只读。结果必须返回所选稳定键
的全部列。只有通配符查询允许新增；投影查询只允许更新直接列和删除。

以下情况明确只读：JOIN/多数据源、CTE、DISTINCT、聚合或分组、集合操作、派生表、视图、缺少
稳定键、稳定键未返回，以及当前驱动无法无损解码稳定键类型。

### 7. 保留单元格语义并保护未保存状态

编辑模型区分 `NULL`、文本、二进制和 `DEFAULT`，不以显示字符串代替值语义。页面切换、重载、
新查询、驱动切换和断开连接在存在暂存变更时被阻止，用户必须先应用或放弃。

## 后果

### 正面

- 不会因为无键表、重复值或复杂查询映射而更新错误的行。
- 并发修改被检测为冲突，批量变更不会部分提交。
- SQL 预览与实际执行一致，所有数据值保持参数化。
- 三种关系库共享契约和规划规则，同时保留占位符、引用和 NULL 比较差异。
- 复杂查询仍可正常查看，并给出具体只读原因。

### 负面

- 每次服务端页面加载多执行一次精确计数，大表上的代价可能明显。
- `OFFSET` 分页在很深的页面仍可能变慢；当前版本没有实现键集分页。
- 原始 SQL 片段虽然经过结构验证，仍可能调用昂贵函数或子查询。
- 严格的稳定键规则会让一些数据库实际可更新、但元数据无法证明安全的表保持只读。
- 查询投影只允许更新已返回的直接列，不能推断可更新视图或复杂数据库规则。

## 备选方案

### 使用物理行标识

未采用。PostgreSQL `ctid`、SQLite `rowid` 等标识并非跨更新稳定，MySQL 也没有统一等价物，
会形成数据库专用且容易失效的隐式行为。

### 没有主键时比较所有列

未采用。重复行无法唯一定位，LOB/浮点/自定义类型比较也可能不可靠；影响多行时才发现问题仍会
放大误操作风险。

### 根据数据库报告的“可更新结果集”直接开放编辑

未采用。SQLx 和统一驱动契约没有跨数据库一致的结果可更新元数据，而且 JOIN、别名和表达式映射
规则差异很大。保守 AST 分析更容易测试和解释。

### 提交时重新生成 SQL

未采用。预览与执行可能因界面状态变化而漂移。保存并执行同一个参数化计划能提供更清晰的确认边界。
